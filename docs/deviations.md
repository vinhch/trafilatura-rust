# Deviations from upstream

Every place this crate departs from upstream Python trafilatura at the pinned release, deliberate or
forced. The code carries `// deviation: D-n` at the spot. A row leaves when the difference is gone,
for example after upstream changed; ids are never reused.

| Id | Upstream behavior | This crate | Reason | Since |
| --- | --- | --- | --- | --- |
| D-1 | `fast=False` by default: readability and jusText run after the main extractor (`external.py`) and can replace its result | Fast mode only: no `fast` option, no readability or jusText, every `options.fast` branch takes the fast side | Keeps the first releases thin; a caller that needs a fallback runs one on a rejection. Porting `fast=False` is Phase 11 | first release |
| D-2 | `lxml.html` parses with libxml2: HTML5 tokenizer, libxml2's own tree construction (no implied `tbody`, no adoption agency) | html5ever: HTML5 tokenizer and tree construction, into the crate's arena tree. SVG and MathML elements carry a namespace in the html5 tree, so name tests (`.//svg`, `self::div`, `iter('a')`) skip them where upstream's libxml2 tree, which has no namespaces, matches them. Such an element reaches the output only because the html5 tree keeps it; `Tree::tostring` writes it by its local name, as upstream's libxml2 tree does. The oracle's own html5 tree (`tools/parity/parity/html5tree.py`) names it `{ns}local`, so lxml writes `ns0:` prefixes there and the generator strips them from its expected HTML | No maintained pure-Rust libxml2 tree builder; FFI to libxml2 brings C, `unsafe` and system-dependent versions. A libxml2-style builder is part of Phase 10 | first release |
| D-3 | Bytes that are not valid UTF-8 are decoded with `charset_normalizer`'s guesses (`utils.py::detect_encoding`); upstream drops a UTF-8 guess, so UTF-8 text with a few stray invalid bytes, where charset_normalizer returns no match, has no candidate and is decoded as UTF-8 with U+FFFD | `chardetng` makes one guess, decoded with `encoding_rs`. UTF-8 text with more than ten valid non-ASCII characters per invalid sequence gets no candidate and takes the U+FFFD fallback. At a ratio of ten or less, upstream may still return no candidate and decode with U+FFFD, while the crate takes the `chardetng` single-byte guess. Every other page also gets the `chardetng` guess, which can differ from upstream's | No maintained Rust port of charset_normalizer; porting it is a project of its own. `chardetng` never answers "none", so the mostly-UTF-8 ratio is a heuristic standing in for charset_normalizer's mojibake check. A parity detector is part of Phase 10 | first release |
| D-4 | Compressed input (gzip, zstd, brotli, zlib) is decompressed (`utils.py::handle_compressed_file`) | Only with the `decompress` feature; the default build parses compressed bytes as they are, except that gzip and zstd bytes without `html` near the start are rejected before decoding (D-12) | HTTP clients decompress before the crate sees the body; keeps three crates out of the default build | first release |
| D-5 | libxml2 has no element-count limit beyond nesting depth 256, and builds no reconstructed copies of formatting elements | The parse stops with `Rejection::TreeTooLarge` once more than `DEFAULT_MAX_NODES` (500,000) elements are created, html5ever's clones of open formatting elements included; a caller sets `max_nodes: None` to lift it; a markup value of an embedded-JSON script (`baseline.py::_render_text`) whose fragment parse hits the limit falls back to the trimmed text, as upstream's `except` branch does for a fragment it cannot parse. A tag (start or end) with more than `MAX_TAG_ATTRIBUTES` (1,000) attributes, and an `html` or `body` element whose attributes merged from repeated tags pass that count, also give `Rejection::TreeTooLarge`; a scan before html5ever reads the input checks the tags and counts duplicate names too, and a markup fragment these caps reject falls back to the trimmed text as for the node limit. Two budgets scale with `max_nodes` and are lifted with it: the attributes created in one parse, reconstructed clones included, may not pass 10 per allowed node (5,000,000 at the default), and html5ever's work on formatting elements may not pass 40 units per allowed node (20,000,000 at the default; one unit is 13 ns). The work is charged where html5ever spends it: once per formatting start tag, against each same-name formatting ancestor of the element the tag creates (the entries Noah's Ark compares are exactly those open elements; the clones of reconstruction and of the adoption agency run no compare and are not charged one) 12 units per pair plus, for each of the two attribute lists, a clone and a sort priced as a shuffled list (one unit per attribute, plus one per attribute and level of a merge sort, plus one per 128 bytes of names per level); 10 units per attribute of every formatting element created, which prices the clones of reconstruction; and once per end tag that html5ever answers with "Formatting element not in scope", the end tag that clones the element's attributes and leaves it in the list. A gate between tokenizer and tree builder drops every token once the budget is crossed, so html5ever's work after the abort is one token's, not the rest of its 8 KiB piece. The budget rejects, although html5ever would finish within about 0.3 s: a page that leaves many same-name formatting elements of distinct attributes open and reconstructs them in every paragraph (paragraphs of `<p><font color=cN size=2>t</p>` cycling 10 colors are rejected from 14,941 and parse at 2,000, cycling 20 colors from 7,550; with every color distinct the open elements reach the depth cut of 256 and the partial tree of 32,641 elements is kept at any length), a page of 95,240 or more paragraphs that each leave an identical `font` of three attributes open (a paragraph costs 210 units), and a page whose same-name formatting ancestors sit before a `td`, `th`, `caption`, `template`, `applet`, `object` or `marquee` marker, which html5ever stops comparing at but the charge still counts | html5ever's tree construction multiplies elements quadratically on a small page (102 KB gives 4.0M elements, peak about 1.3 GB), which would abort an FFI host; 500k is about 18 times the largest corpus page (27,741 elements), and a page of 499,000 paragraphs, just under the limit, peaks at 420 MB of heap in the whole extraction. html5ever's duplicate-attribute check compares each attribute with every earlier one of the same tag (quadratic: one tag of the size of the input cap would take hours), and no corpus tag comes near 100 attributes (the most is 38). The tree builder adds two more attribute costs no single tag triggers (release build, 1,000-attribute `<b>` elements): its Noah's Ark compare clones and sorts both attribute lists for every same-name entry (50 nested `<b>` then 2,000 `<b></b>` took 2.7 s for 259 KB, 200 nested and 2,000 took 11.7 s, a foster-parented and a misnested `</p>` variant 12.0 s and 11.7 s; with shuffled names the same page of 2,000 probes took 2.3 s at 10 MB, because the sorts then do their full work, and names of 70 bytes with a common prefix 2.8 s at 63 MB), reconstruction clones the attributes of every open entry (250 entries and 2,000 `<p>` made 500,000 clones and about 12 GB; 14 names of 14 entries of 1,000 attributes took 1.5 to 2.8 s before the budget tripped, values of 0 to 200 bytes), and 64 MiB of `</b>` after a heavy `<b>` under a `<table>` took 137 s (7 microseconds each, a clone of the attributes). With the budgets those pages end rejected in 0.06 to 0.37 s, in-order names, shuffled names with a 1,000 byte prefix and the reconstruction pages included, even at the 64 MiB input cap. A page the budget does not reject runs at html5ever's own speed, which no budget of this deviation bounds: 64 MiB of comments takes 2.0 to 2.3 s with or without heavy open formatting elements, and 64 MiB of `</x>` takes 2.1 to 2.2 s alone or behind one, 5.0 to 5.1 s behind 20 open formatting elements and 7.1 to 7.3 s behind 40, since each end tag walks the open elements (a heavy element costs the same as one without attributes); behind 250 it takes 28 s, a figure measured with attribute-free elements; the corpus maximum is 10,154 attributes and 62,920 units of work, 492 and 318 times below the budgets, and a page of 20,000 paragraphs with an unclosed `font` is charged 4,199,640 units (21 percent) | first release |
| D-6 | `append` and `insert` of the parent itself or one of its ancestors, and `addnext` and `addprevious` of an ancestor of the anchor, raise `ValueError`; `addnext` and `addprevious` on an anchor without a parent raise `TypeError` | `dom::Tree::{append, insert, add_next, add_previous}` return without changing the tree in those cases | Keeps the tree primitives infallible: a `Result` on every edit would add a branch at each call site for cases the pipeline is not expected to reach. Adding a node next to itself is a no-op in lxml too, so it is not part of this row | first release |
| D-7 | `extract(prune_xpath=...)` compiles the caller's XPath strings and removes what they select (`core.py`) | The option does not exist: the crate has no XPath engine and takes no caller selectors. Followup F-16, after Phase 7: a caller-supplied prune needs a public tree or predicate API, which Phase 3 does not have | The selectors are hand-written matchers, one function per upstream expression, so the crate can evaluate only the expressions it ships | Phase 3b |
| D-8 | `tree_cleaning` with `images` on takes `img` out of `MANUALLY_STRIPPED`; when a caller has removed it from that list, `list.remove` raises `ValueError`, which `bare_extraction` catches: it logs "discarding data" and `extract` returns `None` | `tree_cleaning_with` strips what its list holds and raises nothing when `img` is missing from it. This also departs from the porting rule that a raise upstream catches becomes an `Err` reaching the same handler (`AGENTS.md`, Exceptions) | Only a caller-supplied list can reach it, and no public option offers one yet. The typed rejection belongs to the change that adds the element lists as options | Phase 3c |
| D-9 | Table construction (`handle_table`) builds as many cells as the `rowspan` and `colspan` attributes ask for, however many | Fails with `Rejection::TreeTooLarge` once table construction has minted `MAX_OUTPUT_NODES` (2 x `DEFAULT_MAX_NODES`, 1,000,000) cells in one tree; the count covers every table of one extraction and every cascade pass, and ignores the parse and the tree copies, so the arena may grow past that size. A failure inside the recall retry of the cascade is swallowed, as upstream swallows any exception there, so the first-pass text stands where upstream's unbounded retry could have replaced it | A 35 KB table of rowspan and colspan cells builds 10M nodes (about 2 GB), which would abort an FFI host; `max_nodes` only limits the parse; a table of exactly 1,000,000 cells peaks at 530 MB of heap in the whole extraction, about 530 bytes per cell | Phase 3d |
| D-10 | Python's recursion limits cut two walks of a JSON-LD script: `_walk_json` recurses on `@graph` and `mainEntity`, and `str(item.get("@type"))` recurses into a nested value. The `RecursionError` ends that script's walk, and the bodies and teasers collected so far stay. The depth where it fails depends on the caller's stack: 1000 nested levels with a body each give 996 bodies through a top-level `baseline` and 992 through `extract` | Fixed caps, the `extract` values: a dict on level 992 ends the walk after its own texts and teaser, whether or not it has a `@graph` or `mainEntity` (upstream enters the next frame for an absent container too), and a `@type` value with an object nested deeper than 9996 levels (itself counted as 1, scalars included) ends it before the teaser test. The nesting cap of the parse (9998) matches Python and is not part of this row | `walk_json` and the `@type` search are loops over an explicit stack, so a deep document never overflows the host's stack; a cap that follows the caller's stack depth would make the output depend on the host | Phase 3f |
| D-11 | `extract` and `bare_extraction` take input of any size; `max_file_size` (20,000,000) caps only decompressed output | Input longer than `max_input_bytes` (default 64 MiB) is rejected with `Rejection::InputTooLarge` before decompression, decoding or parsing, on every loading path; `Options::max_input_bytes` changes or lifts it for an `Extractor`, while the free `html2txt` always uses the default | A page that bypasses `max_nodes` with large text still costs several times its size in memory, and an out-of-memory abort takes down an FFI host; 64 MiB is above the largest page the host accepts (50 MB) | first release |
| D-12 | Binary input is decoded and parsed in full; `load_html` returns `None` when the first 50 characters lack `html` and the tree has fewer than 2 children, which is the usual result for such files | Input that starts with the magic bytes of zip (`PK\x03\x04`), PDF (`%PDF-`), PNG, JPEG (`\xff\xd8\xff`), GIF (`GIF87a`, `GIF89a`), WebP (`RIFF` and `WEBP`), gzip or zstd and has no `html` (any case) in its first 200 bytes is rejected with `Rejection::EmptyTree` after decompression, before decoding and parsing. Any input with such a prefix whose parse would give 2 or more children differs, text included: upstream returns a tree for `GIF89a<p>a</p><p>b</p>`, this crate returns `EmptyTree` | Decoding and parsing a large binary file costs time and several times its size in memory for a result that is `None` | first release |
| D-16 | `courlan.clean.decode_punycode` decodes an `xn--` label with `part.encode("utf8").decode("idna")`. `ToUnicode` encodes the decoded text again through `ToASCII`, which runs nameprep (RFC 3491: Unicode 3.2 stringprep mapping, prohibited characters, the RFC 3454 section 6 bidi rule), and raises when the result differs from the lowercased label; `decode_punycode` then keeps the label encoded | `pyidna::decode_label` runs the rest of `ToUnicode` and `ToASCII` (punycode decode, the `xn--` check on a non-ASCII text, the 63-byte limit, the comparison with the lowercased label) and leaves nameprep out. A label whose decoded text nameprep would map (non-ASCII case folding, `U+00AD`, `U+FB00`; ASCII case folding is reproduced), prohibit (controls, noncharacters) or reject on the bidi rule decodes here and stays encoded upstream | Nameprep needs the Unicode 3.2 tables and a normalizer for them; one corpus page decodes any `xn--` label at all, and it is not of that kind | Phase 4a |
| D-17 | A punycode label whose insertion position reaches 2**63 or more (`xn--` and 40 digits `9` then `a`) makes `encodings.punycode` build a `UnicodeDecodeError` with a start past `ssize_t`, which raises `OverflowError`, not `UnicodeError`. `decode_punycode` catches only `UnicodeError`, so the exception leaves `normalize_url` and `metadata.py` | `pyidna::decode_label` returns `None` for such a label, which stays encoded, and extraction goes on. A position between the code point limit and 2**63 raises `UnicodeError` upstream and gives `None` here too | `decode_label` returns `Option`, as every other `UnicodeError` is `None`; an exception out of metadata for a hostile host label is not a result worth reproducing | Phase 4a |
