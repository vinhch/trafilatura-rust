# Deviations from upstream

Every place this crate departs from upstream Python trafilatura at the pinned release, deliberate or
forced. The code carries `// deviation: D-n` at the spot. A row leaves when the difference is gone,
for example after upstream changed; ids are never reused.

| Id | Upstream behavior | This crate | Reason | Since |
| --- | --- | --- | --- | --- |
| D-1 | `fast=False` by default: readability and jusText run after the main extractor (`external.py`) and can replace its result | Fast mode only: no `fast` option, no readability or jusText, every `options.fast` branch takes the fast side | Keeps the first releases thin; a caller that needs a fallback runs one on a rejection. Porting `fast=False` is followup F-6 | first release |
| D-2 | `lxml.html` parses with libxml2: HTML5 tokenizer, libxml2's own tree construction (no implied `tbody`, no adoption agency) | html5ever: HTML5 tokenizer and tree construction, into the crate's arena tree. SVG and MathML elements carry a namespace in the html5 tree, so name tests (`.//svg`, `self::div`, `iter('a')`) skip them where upstream's libxml2 tree, which has no namespaces, matches them. Such an element reaches the output only because the html5 tree keeps it; `Tree::tostring` writes it by its local name, as upstream's libxml2 tree does. The oracle's own html5 tree (`tools/parity/parity/html5tree.py`) names it `{ns}local`, so lxml writes `ns0:` prefixes there and the generator strips them from its expected HTML | No maintained pure-Rust libxml2 tree builder; FFI to libxml2 brings C, `unsafe` and system-dependent versions. A libxml2-style builder is followup F-7 | first release |
| D-3 | Bytes that are not valid UTF-8 are decoded with `charset_normalizer`'s guesses (`utils.py::detect_encoding`); upstream drops a UTF-8 guess, so UTF-8 text with a few stray invalid bytes, where charset_normalizer returns no match, has no candidate and is decoded as UTF-8 with U+FFFD | `chardetng` makes one guess, decoded with `encoding_rs`. UTF-8 text with more than ten valid non-ASCII characters per invalid sequence gets no candidate and takes the U+FFFD fallback. At a ratio of ten or less, upstream may still return no candidate and decode with U+FFFD, while the crate takes the `chardetng` single-byte guess. Every other page also gets the `chardetng` guess, which can differ from upstream's | No maintained Rust port of charset_normalizer; porting it is a project of its own. `chardetng` never answers "none", so the mostly-UTF-8 ratio is a heuristic standing in for charset_normalizer's mojibake check. A parity detector is followup F-8 | first release |
| D-4 | Compressed input (gzip, zstd, brotli, zlib) is decompressed (`utils.py::handle_compressed_file`) | Only with the `decompress` feature; the default build parses compressed bytes as they are | HTTP clients decompress before the crate sees the body; keeps three crates out of the default build | first release |
| D-5 | libxml2 has no element-count limit beyond nesting depth 256, and builds no reconstructed copies of formatting elements | The parse stops with `Rejection::TreeTooLarge` once more than `DEFAULT_MAX_NODES` (1,000,000) elements are created, html5ever's clones of open formatting elements included; a caller sets `max_nodes: None` to lift it; a markup value of an embedded-JSON script (`baseline.py::_render_text`) whose fragment parse hits the limit falls back to the trimmed text, as upstream does when the parse raises | html5ever's tree construction multiplies elements quadratically on a small page (102 KB gives 4.0M elements, peak about 1.3 GB), which would abort an FFI host; 1M is about 36 times the largest corpus page (27,741 elements) | first release |
| D-6 | `append` and `insert` of the parent itself or one of its ancestors, and `addnext` and `addprevious` of an ancestor of the anchor, raise `ValueError`; `addnext` and `addprevious` on an anchor without a parent raise `TypeError` | `dom::Tree::{append, insert, add_next, add_previous}` return without changing the tree in those cases | Keeps the tree primitives infallible: a `Result` on every edit would add a branch at each call site for cases the pipeline is not expected to reach. Adding a node next to itself is a no-op in lxml too, so it is not part of this row | first release |
| D-7 | `extract(prune_xpath=...)` compiles the caller's XPath strings and removes what they select (`core.py`) | The option does not exist: the crate has no XPath engine and takes no caller selectors. Followup F-16, after Phase 7: a caller-supplied prune needs a public tree or predicate API, which Phase 3 does not have | The selectors are hand-written matchers, one function per upstream expression, so the crate can evaluate only the expressions it ships | Phase 3b |
| D-8 | `tree_cleaning` with `images` on takes `img` out of `MANUALLY_STRIPPED`; when a caller has removed it from that list, `list.remove` raises `ValueError`, which `bare_extraction` catches: it logs "discarding data" and `extract` returns `None` | `tree_cleaning_with` strips what its list holds and raises nothing when `img` is missing from it. This also departs from the porting rule that a raise upstream catches becomes an `Err` reaching the same handler (`AGENTS.md`, Exceptions) | Only a caller-supplied list can reach it, and no public option offers one yet. The typed rejection belongs to the change that adds the element lists as options | Phase 3c |
| D-9 | Table construction (`handle_table`) builds as many cells as the `rowspan` and `colspan` attributes ask for, however many | Fails with `Rejection::TreeTooLarge` once the arena holds more than `MAX_OUTPUT_NODES` (4 x `DEFAULT_MAX_NODES`) nodes while a table cell is created. A failure inside the recall retry of the cascade is swallowed, as upstream swallows any exception there, so the first-pass text stands where upstream's unbounded retry could have replaced it | A 35 KB table of rowspan and colspan cells builds 10M nodes (about 2 GB), which would abort an FFI host; `max_nodes` only limits the parse | Phase 3d |
| D-10 | Python's recursion limits cut two walks of a JSON-LD script: `_walk_json` recurses on `@graph` and `mainEntity`, and `str(item.get("@type"))` recurses into a nested value. The `RecursionError` ends that script's walk, and the bodies and teasers collected so far stay. The depth where it fails depends on the caller's stack: 1000 nested levels with a body each give 996 bodies through a top-level `baseline` and 992 through `extract` | Fixed caps, the `extract` values: a dict on level 992 ends the walk after its own texts and teaser, whether or not it has a `@graph` or `mainEntity` (upstream enters the next frame for an absent container too), and a `@type` value with an object nested deeper than 9996 levels (itself counted as 1, scalars included) ends it before the teaser test. The nesting cap of the parse (9998) matches Python and is not part of this row | `walk_json` and the `@type` search are loops over an explicit stack, so a deep document never overflows the host's stack; a cap that follows the caller's stack depth would make the output depend on the host | Phase 3f |
